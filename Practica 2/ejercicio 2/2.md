# Ejercicio 2 · Figuras ordenadas por área

## Enunciado

> Redefina la clase `PaintTest` del ejercicio 6 de la práctica 1 de manera de
> imprimir las figuras geométricas ordenadas de acuerdo al valor de su área.
> Defina la comparación entre figuras geométricas usando la siguiente regla: una
> figura A es menor que una figura B si el área de A es menor que el área de B.
> Use para ordenar el arreglo de figuras los métodos de ordenación disponibles
> en la clase `java.util.Arrays`.

> **Nota.** En el repositorio, la carpeta `Practica 1/ejercicio 5/` con las
> figuras quedó con los archivos vacíos, así que no había clases que redefinir.
> La jerarquía está implementada acá desde cero y de forma autocontenida, con la
> mínima estructura que el enunciado necesita: una superclase abstracta con
> `area()` y varias subclases concretas.

## La idea: `Comparable`

Para que `Arrays.sort(figuras)` sepa ordenar, las figuras tienen que declarar
**cuál es su orden natural**. Eso se hace implementando la interface
`java.lang.Comparable`:

```java
public interface Comparable<T> {
    int compareTo(T o);
}
```

El contrato de `compareTo` es devolver un entero con **el signo** que indica la
relación, no la diferencia:

| Devuelve | Significa |
| --- | --- |
| negativo | `this` es menor que `o` |
| `0` | son equivalentes en este orden |
| positivo | `this` es mayor que `o` |

La regla del enunciado —A es menor que B si el área de A es menor que la de B—
se traduce directo:

```java
public abstract class FiguraGeometrica implements Comparable<FiguraGeometrica> {

    public abstract double area();

    @Override
    public int compareTo(FiguraGeometrica otra) {
        return Double.compare(this.area(), otra.area());
    }
}
```

`compareTo` va en la **superclase abstracta**, no en cada subclase: la regla de
comparación es la misma para todas las figuras y está definida en términos de
`area()`, que es abstracto. Cada subclase aporta su fórmula de área y el orden
sale gratis. Esto es polimorfismo en el sentido más útil: el algoritmo de
comparación se escribe una vez, contra el contrato.

### Por qué `Double.compare` y no una resta

La tentación es escribir:

```java
return (int) (this.area() - otra.area());   // MAL
```

Y está mal por dos razones, las dos verificadas:

```
(int)(3.14 - 3.99) = 0            -> dice IGUALES, cuando 3.14 < 3.99
(int)(3e9 - 1.0)   = 2147483647   -> saturado a Integer.MAX_VALUE
```

1. **Truncamiento.** El cast a `int` descarta la parte decimal. Cualquier
   diferencia de áreas menor que 1 se convierte en `0`, o sea "equivalentes", y
   el orden sale mal. Con figuras chicas esto pasa todo el tiempo.
2. **Desborde.** Con áreas grandes la diferencia no cabe en un `int` y el signo
   puede terminar invertido, que es la peor forma de falla: `sort` puede tirar
   `IllegalArgumentException: Comparison method violates its general contract!`
   o simplemente devolver el arreglo mal ordenado.

`Double.compare(a, b)` devuelve `-1`, `0` o `1` y además trata bien los casos
raros de punto flotante (`NaN`, `-0.0`).

## Los métodos de `java.util.Arrays` que se usan

| Llamada | Qué hace |
| --- | --- |
| `Arrays.sort(figuras)` | ordena por el **orden natural** (`compareTo`) |
| `Arrays.sort(figuras, cmp)` | ordena con un `Comparator` externo |
| `Arrays.sort(figuras, 0, 3)` | ordena solo el tramo `[0, 3)` |
| `Arrays.binarySearch(figuras, f)` | busca en **O(log n)**, exige el arreglo ya ordenado con el mismo criterio |

Sobre `Arrays.sort` para objetos: usa **TimSort**, que es estable —dos figuras
de área igual conservan su orden relativo previo— y `O(n log n)` en el peor
caso. La versión para primitivas (`int[]`, `double[]`) usa en cambio un quicksort
dual-pivot, que no es estable, pero para primitivas la estabilidad no se puede
observar.

## `Comparable` vs `Comparator`

Son las dos formas de definir un orden, y conviene tener clara la diferencia
porque el ejercicio se resuelve con la primera pero la segunda aparece enseguida:

| | `Comparable` | `Comparator` |
| --- | --- | --- |
| Dónde vive | **dentro** de la clase que se ordena | en un objeto **aparte** |
| Método | `compareTo(T o)` | `compare(T a, T b)` |
| Cuántos | **uno** por clase | tantos como se quiera |
| Sirve para | el orden "obvio" del tipo | órdenes alternativos o ajenos a la clase |
| Requiere | modificar la clase | nada |

El enunciado pide el orden **por área**, que es el orden natural de una figura,
así que va como `Comparable`. Pero `TestPaint` muestra también los otros, que se
consiguen **sin tocar ninguna de las clases de figuras**:

```java
Arrays.sort(figuras, Comparator.reverseOrder());                        // area descendente
Arrays.sort(figuras, Comparator.comparingDouble(FiguraGeometrica::perimetro));
Arrays.sort(figuras, Comparator.comparing(FiguraGeometrica::getNombre));
```

Ahí está la ventaja de `Comparator`: agregar un criterio de orden no es un
cambio en la jerarquía. Es el mismo argumento que aparece en el
[ejercicio 3.b](../ejercicio%203/3.md) a favor de la composición.

## Una advertencia del contrato

La documentación de `Comparable` recomienda que el orden natural sea
**consistente con `equals`**: que `a.compareTo(b) == 0` implique
`a.equals(b)`. Acá **no** lo es, y a propósito: un `Cuadrado(l=5)` y un
`Rectangulo(5x5)` tienen la misma área, así que `compareTo` devuelve `0`, pero no
son el mismo objeto ni son `equals`.

Eso es legal —la propia `java.math.BigDecimal` tiene esta inconsistencia— pero
hay que saber dónde muerde: las colecciones ordenadas `TreeSet` y `TreeMap` usan
`compareTo` en lugar de `equals` para decidir si un elemento ya está. Metiendo
esas dos figuras en un `TreeSet`, la segunda **se descarta** como duplicada, aun
siendo un objeto distinto. Para el enunciado, que ordena un arreglo, no hay
problema.

encierra más área por unidad de perímetro, así que los dos órdenes no pueden
coincidir.
