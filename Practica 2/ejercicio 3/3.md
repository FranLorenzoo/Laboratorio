# Ejercicio 3 · `HashSetAgregados`: herencia vs. composición

## Código analizado

```java
public class HashSetAgregados<E> extends HashSet<E> {

  private int cantidadAgregados = 0;

  public HashSetAgregados() {
  }

  public HashSetAgregados(int initCap, float loadFactor) {
     super(initCap, loadFactor);
  }

  @Override public boolean add(E e) {
    cantidadAgregados++;
    return super.add(e);
  }

  @Override public boolean addAll(Collection<? extends E> c) {
     cantidadAgregados += c.size();
     return super.addAll(c);
  }

  public int getCantidadAgregados() {
     return cantidadAgregados;
  }
}
```

El código **compila**. El problema es de comportamiento.

## a) ¿Tiene el funcionamiento esperado?

**No.** Con `add()` funciona; con `addAll()` cuenta **el doble**:

```
--- Solo add(), 3 veces ---
size()                = 3
getCantidadAgregados()= 3
esperado              = 3   -> BIEN

--- addAll() de una coleccion de 3 elementos ---
size()                = 3
getCantidadAgregados()= 6
esperado              = 3   -> MAL
```

### ¿Por qué?

Porque **`HashSet.addAll()` está implementado llamando a `add()`**. `HashSet` no
define `addAll`: lo hereda de `AbstractCollection`, cuya implementación es, en
esencia:

```java
public boolean addAll(Collection<? extends E> c) {
    boolean modified = false;
    for (E e : c)
        if (add(e))            // <-- llamada a add()
            modified = true;
    return modified;
}
```

Y ese `add(e)` es una **invocación polimórfica**: no llama al `add` de
`AbstractCollection`, llama al `add` **del objeto real**, que es el nuestro. Así
que cada elemento se cuenta dos veces:

1. una en `cantidadAgregados += c.size()`, de nuestro `addAll`;
2. otra en `cantidadAgregados++`, de nuestro `add`, invocado por dentro de
   `super.addAll(c)`.

La prueba lo muestra en vivo, con una subclase anónima que imprime cada llamada:

```
--- La causa: HashSet.addAll llama a add() ---
Llamando a s4.addAll([p, q]):
    add("p") invocado desde addAll
    add("q") invocado desde addAll
getCantidadAgregados()= 4  (2 de c.size() + 2 de los add)
```

### Un segundo error, independiente del primero

`c.size()` es la cantidad de elementos **del argumento**, no la cantidad de
elementos que efectivamente entraron al conjunto. Un `Set` descarta duplicados:

```
--- addAll() con un repetido: [x, x, y] ---
size()                = 2   (x se guarda una vez)
getCantidadAgregados()= 6
```

De `[x, x, y]` el conjunto guarda 2 elementos, y el contador dice 6.

### ¿Tiene relación con la herencia?

**Sí, es el núcleo del problema.** Y no se arregla borrando el `addAll`.

Si se elimina la redefinición de `addAll`, el contador da bien... **por
casualidad**: da bien porque `HashSet.addAll` hoy llama a `add`. Eso es un
**detalle de implementación interno** de la superclase, que su documentación no
promete. Si una versión futura del JDK optimizara `addAll` para escribir directo
en la tabla hash sin pasar por `add`, el contador quedaría en cero y nuestra
clase se rompería **sin que nadie haya tocado una línea de nuestro código**.

Esto es lo que se conoce como el problema de la **clase base frágil** (*fragile
base class*), y su causa es que **la herencia rompe el encapsulamiento**: la
subclase no depende solamente de la *interfaz* de la superclase, sino de **cómo
está escrita por dentro** — en particular, de qué métodos propios se llaman entre
sí (*self-use*). Esa información no es parte del contrato público.

De ahí la regla general: **heredar solo cuando hay una relación "es-un" genuina
y la superclase está diseñada y documentada para ser extendida.** `HashSet` no lo
está.

Vale notar el contraste con el
[ejercicio 3.2 de la práctica 1](../../Practica%201/ejercicio%203/3.2.md): ahí
heredar de `java.io.File` fallaba en **compilación**, y el compilador avisaba.
Acá compila perfecto y falla en **ejecución**, silenciosamente. El segundo caso
es bastante peor.

## b) Alternativa: composición

> ¿Qué interface usaría?

**`java.util.Set<E>`.** En lugar de *ser* un `HashSet` por herencia, la clase
**implementa `Set`** (para poder usarse en cualquier lugar donde se espere un
conjunto) y **contiene** un `Set` privado al que le delega el trabajo real:

```java
public class ConjuntoConAgregados<E> implements Set<E> {

    private final Set<E> elementos;        // composicion: lo CONTIENE
    private int cantidadAgregados = 0;

    @Override
    public boolean add(E e) {
        boolean agregado = elementos.add(e);
        if (agregado) {                     // solo si realmente entro
            cantidadAgregados++;
        }
        return agregado;
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        boolean cambio = false;
        for (E e : c) {
            if (add(e)) {                   // NUESTRO add: se cuenta una sola vez
                cambio = true;
            }
        }
        return cambio;
    }

    // ... el resto de los metodos de Set se delegan en 'elementos'
}
```

Archivo: [`ConjuntoConAgregados.java`](ConjuntoConAgregados.java).

Resultado:

```
--- addAll() de 3 elementos ---
size()                = 3
getCantidadAgregados()= 3
esperado              = 3   -> BIEN

--- addAll() con un repetido: [x, x, y] ---
size()                = 2
getCantidadAgregados()= 2   (el duplicado no se agrego, no se cuenta)
```

### Ventajas respecto de la original

| | Herencia (original) | Composición |
| --- | --- | --- |
| Depende de cómo está implementado `HashSet` por dentro | **sí** | no |
| `addAll` cuenta bien | no (el doble) | sí |
| Cuenta duplicados no agregados | sí | no |
| Se rompe si cambia el JDK | puede | no |
| Qué implementación de `Set` usa por dentro | fija: `HashSet` | cualquiera |
| Superficie expuesta | todo `HashSet` | solo `Set` |

Las dos primeras son la respuesta directa; las otras tres vale desarrollarlas:

- **Independencia del delegado.** El constructor acepta el `Set` a usar, así que
  la misma clase sirve sobre `HashSet`, `TreeSet` o `LinkedHashSet`. Con herencia
  la elección quedaba clavada en el `extends`.
- **Superficie controlada.** Heredando, la clase expone además todo lo que
  `HashSet` tenga hoy y lo que le agreguen mañana. Un método nuevo en `HashSet`
  aparecería automáticamente en `HashSetAgregados`, sin pasar por el contador y
  potencialmente violando su invariante. Delegando, solo existe lo que se
  escribió.
- **Contrato explícito.** Al implementar `Set`, el compilador obliga a decidir
  qué hace cada método. No hay comportamiento heredado por omisión.

El costo es el **código repetitivo**: hay que escribir los ~15 métodos de `Set`
aunque casi todos sean una línea de reenvío. Es exactamente lo que resuelve el
punto c).

## c) Diseño general: reenvío + decoradores

> Diseñe e implemente una solución que permita fácilmente definir nuevos tipos de
> `Set` con distintas características.

El código de delegación de b) no tiene nada específico de "contar agregados": es
puro reenvío. Se lo extrae a una clase reutilizable y los contadores pasan a ser
**decoradores** sobre ella.

### La pieza base: `SetForwarding`

```java
public class SetForwarding<E> implements Set<E> {

    protected final Set<E> delegado;

    public SetForwarding(Set<E> delegado) { this.delegado = delegado; }

    @Override public boolean add(E e)         { return delegado.add(e); }
    @Override public boolean remove(Object o) { return delegado.remove(o); }
    // ... los 15 metodos de Set, todos reenviados
}
```

Archivo: [`SetForwarding.java`](SetForwarding.java). Sola no hace nada; su valor
es que **el código repetitivo se escribe una única vez**.

### Los decoradores

Cada característica nueva es una subclase que redefine **solo los métodos que le
importan**:

```java
public class SetConAgregados<E> extends SetForwarding<E> {
    private int cantidadAgregados = 0;
    @Override public boolean add(E e) { ... }         // 2 metodos
    @Override public boolean addAll(...) { ... }
}
```

Archivos: [`SetConAgregados.java`](SetConAgregados.java) y
[`SetConRemovidos.java`](SetConRemovidos.java).

Este es el **patrón Decorator**: envolver un objeto en otro del mismo tipo, que
agrega comportamiento antes o después de delegar. Es el mismo mecanismo con que
está construido `java.io`:

```java
new BufferedReader(new InputStreamReader(System.in))
```

Y a diferencia del [Singleton de la práctica 1](../../Practica%201/ejercicio%204/4.md),
que restringe la creación de instancias, este patrón compone comportamiento.

### `SetConRemovidos`: hay más vías que en agregar

Contar removidos es más delicado, porque un elemento puede salir por cinco
caminos distintos: `remove(Object)`, `removeAll`, `retainAll`, `clear()` y
`iterator().remove()`. Los cinco están cubiertos.

Dos decisiones de implementación que vale señalar:

**1. Se cuenta por diferencia de tamaño**, no por el tamaño del argumento — que
es justamente el error del código original:

```java
@Override
public boolean removeAll(Collection<?> c) {
    int antes = size();
    boolean cambio = super.removeAll(c);
    cantidadRemovidos += antes - size();     // lo que realmente salio
    return cambio;
}
```

**2. Se envuelve el iterador**, porque si no, un `for` con `it.remove()` vaciaría
el conjunto sin registrar nada:

```java
@Override
public Iterator<E> iterator() {
    final Iterator<E> it = super.iterator();
    return new Iterator<E>() {
        @Override public boolean hasNext() { return it.hasNext(); }
        @Override public E next()          { return it.next(); }
        @Override public void remove()     { it.remove(); cantidadRemovidos++; }
    };
}
```

Este detalle es fácil de olvidar y muestra que la composición no es automática:
hay que pensar todas las vías por las que el estado puede cambiar. La diferencia
con la herencia es que acá **son todas visibles en el contrato de `Set`**,
mientras que en la herencia dependían de cómo `HashSet` se llamara a sí misma.

### Lo que el diseño habilita

Los decoradores envuelven **cualquier `Set`**, así que funcionan sobre cualquier
implementación y **se pueden apilar**:

```java
SetConAgregados<String> interno = new SetConAgregados<>(new TreeSet<>());
SetConRemovidos<String> apilado = new SetConRemovidos<>(interno);
```

```
--- Los decoradores se APILAN ---
contenido             = [m, o]
agregados (interno)   = 3
removidos (externo)   = 1
```

Y agregar una característica nueva —un `Set` que registre cada operación en un
log, uno de solo lectura, uno con tamaño máximo, uno sincronizado— cuesta una
subclase de `SetForwarding` con dos o tres métodos. Con la herencia de `HashSet`
cada variante habría que reescribirla desde cero, y todas arrastrarían el mismo
problema de fragilidad.

## Lo que deja el ejercicio

La regla que resume todo es **"preferir composición a herencia"**: usar herencia
para *reutilizar código* acopla la subclase a los detalles internos de la
superclase, y ese acoplamiento no aparece en ninguna firma ni lo detecta el
compilador. La composición cuesta más código repetitivo —mitigado por una clase
de reenvío— y a cambio da una dependencia que es solo del contrato público.

La herencia sigue siendo la herramienta correcta cuando hay un "es-un" real y la
superclase fue **diseñada para extenderse**, documentando qué métodos son
redefinibles y cómo se usan entre sí. `AbstractSet` y `AbstractCollection`, por
ejemplo, sí están pensadas para eso.
