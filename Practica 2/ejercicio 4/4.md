## a) ¿Cómo se serializa un objeto?

### Qué es

**Serializar** es convertir un objeto en memoria en una **secuencia de bytes**
que puede escribirse en un archivo, guardarse en una base de datos o enviarse
por la red. **Deserializar** es el proceso inverso: reconstruir el objeto a
partir de esos bytes.

Lo que se guarda es el **estado** del objeto —los valores de sus campos— junto
con la información de **qué clase** es, necesaria para poder reconstruirlo.

### Con qué fin

| Fin | Ejemplo |
| --- | --- |
| **Persistencia** | guardar el estado de la aplicación y recuperarlo en la próxima ejecución |
| **Comunicación** | enviar objetos entre dos procesos o entre cliente y servidor |
| **Copia profunda** | serializar y deserializar produce un objeto nuevo, independiente del original |
| **Caché / sesión** | guardar la sesión de un usuario fuera del proceso que la atiende |

En todos los casos el problema que resuelve es el mismo: un objeto vive en la
memoria de **un** proceso, y su dirección no significa nada fuera de él. Para
cruzar ese límite hay que convertirlo en algo autocontenido: bytes.

### Los tres pasos en Java

**1 · Marcar la clase con `Serializable`**

```java
public abstract class FiguraGeometrica
        implements Comparable<FiguraGeometrica>, Serializable {
```

`java.io.Serializable` es una **interface marcadora** (*marker interface*): no
declara ningún método. La prueba lo verifica:

```
Circulo instanceof Serializable ? true
Metodos que declara Serializable: 0
```

Solo señala que la clase **autoriza** su serialización; el trabajo lo hace la
JVM por reflexión. Sin esa marca, intentar serializar tira
`NotSerializableException`. Es un mecanismo de opt-in deliberado: serializar
expone los campos privados de la clase, así que tiene que ser una decisión
explícita.

Alcanza con implementarla en la **superclase**: `Serializable` se hereda, así que
`Circulo`, `Rectangulo`, `Cuadrado` y `TrianguloRectangulo` quedan serializables
sin tocarlas.

**2 · Escribir con `ObjectOutputStream`**

```java
try (ObjectOutputStream out =
             new ObjectOutputStream(new FileOutputStream("figuras.ser"))) {
    out.writeObject(originales);
}
```

Se serializa el arreglo completo en una sola llamada: los arreglos son
serializables si su tipo de elemento lo es.

Nótese que `ObjectOutputStream` **envuelve** un `FileOutputStream`. Es el mismo
patrón Decorator del [ejercicio 3.c](../ejercicio%203/3.md): un stream que
agrega comportamiento —convertir objetos en bytes— delegando la escritura en
otro.

**3 · Leer con `ObjectInputStream`**

```java
try (ObjectInputStream in =
             new ObjectInputStream(new FileInputStream("figuras.ser"))) {
    recuperadas = (FiguraGeometrica[]) in.readObject();
}
```

`readObject()` devuelve `Object`, así que hace falta el cast, y puede lanzar
`ClassNotFoundException` si la clase del objeto no está en el classpath.

### Qué se conserva

```
--- Que se conservo y que no ---
Cantidad de figuras:  4
Tipos concretos:      TrianguloRectangulo, Cuadrado, Circulo, Rectangulo
Siguen ordenadas?     true
Areas identicas?      true
```

El **tipo concreto** se conserva: lo que vuelve del archivo no son
`FiguraGeometrica` genéricas, son `Circulo`, `Cuadrado`, etc. La serialización
guarda la clase real de cada objeto, así que el polimorfismo sigue funcionando
después de deserializar — por eso `toString()` y `area()` siguen dando lo
correcto para cada figura.

### Tres detalles que conviene tener claros

**El grafo de objetos se sigue completo.** `writeObject` no serializa solo el
objeto que recibe: recorre todas las referencias que salen de él, y las que salen
de esas, recursivamente. Por eso **todo** lo alcanzable tiene que ser
serializable, o hay que marcarlo `transient`. Y por eso también maneja las
referencias compartidas y los ciclos sin duplicar objetos ni colgarse.

**Se crean objetos nuevos.**

```
--- Identidad: son objetos NUEVOS ---
originales[0] == recuperadas[0] ? false
Misma clase?                     true
```

Deserializar **no** devuelve el objeto original: construye otro con el mismo
estado. Esto es lo que la vuelve útil como copia profunda, y también es el motivo
por el que la serialización **rompe el patrón Singleton** del
[ejercicio 4 de la práctica 1](../../Practica%201/ejercicio%204/4.md): si
`Logger` fuera serializable, deserializarlo produciría una **segunda** instancia,
sin pasar por `getInstance()` ni por el constructor privado. Se evita
implementando `readResolve()`, o —más simple— usando un `enum`, que es inmune por
definición.

**El constructor no se ejecuta.**

```
--- El constructor NO se ejecuta al deserializar ---
nombre recuperado: Triangulo(6.0x8.0)
```

La deserialización asigna los campos **directamente**, por reflexión, sin pasar
por ningún constructor de la clase. Se ve en que `nombre` es `final` y aparece
correctamente asignado, aunque ningún constructor corrió. Las consecuencias:

- Las **validaciones** que estén en el constructor **no se aplican**. Un archivo
  serializado adulterado puede producir un objeto en estado imposible: un
  `Circulo` con radio negativo, por ejemplo. Es la razón por la que la
  deserialización de datos no confiables se considera un riesgo de seguridad.
- Los campos que el constructor inicializaba y no están en el stream quedan en
  su valor por defecto.

### El campo `transient`

`FiguraGeometrica` tiene un caché del área marcado `transient`:

```java
private transient Double areaCache;
```

`transient` significa **"no serializar este campo"**. Al deserializar queda en su
valor por defecto (`null` acá):

```
--- El campo transient NO se serializo ---
Cache cargado tras deserializar? false
areaCacheada() lo recalcula:      24.00
Cache cargado ahora?              true
```

Se usa para tres cosas:

1. **Datos derivados**, que se pueden recalcular — el caché de este ejemplo.
2. **Datos no serializables**, como una conexión abierta, un `Thread` o un
   `Socket`, que no tienen sentido fuera del proceso.
3. **Datos sensibles** que no deben salir a un archivo, como una contraseña.

## b) Relación con el `serialVersionUID`

### Qué es

`serialVersionUID` es un `long` que identifica la **versión de la clase** a
efectos de serialización:

```java
private static final long serialVersionUID = 1L;
```

Se escribe en el stream junto con los datos. Al deserializar, la JVM compara el
UID guardado con el de la clase que tiene cargada:

- **coinciden** → adelante;
- **no coinciden** → `InvalidClassException`, y no se lee nada.

### Si no se lo declara, la JVM lo calcula

Y ahí está el problema. El UID calculado sale de un hash de la **estructura** de
la clase: nombre, interfaces, campos, métodos y sus modificadores. Cualquier
cambio en esa estructura —agregar un campo, cambiar un tipo, incluso agregar un
método— produce un UID distinto, y **todo lo serializado antes deja de poder
leerse**.

Peor: el algoritmo depende del compilador, así que dos compilaciones de la
*misma* clase con distintos compiladores pueden dar UIDs diferentes.

Por eso `javac -Xlint:serial` avisa cuando falta, **en cada clase de la
jerarquía**:

```
Circulo.java:1: warning: [serial] serializable class Circulo has no definition of serialVersionUID
```

Es una advertencia, no un error: la clase compila igual. En este ejercicio se
declaró en las cinco clases, y con eso el `-Xlint:serial` queda limpio.

### El experimento

En [`uid/`](uid) está la prueba, reproducible con
[`uid/experimento.sh`](uid/experimento.sh). Una clase `Pieza` con campos
`{codigo, cantidad}` se serializa con la versión 1, y se intenta leer con tres
versiones distintas:

| Versión | Cambio | Resultado |
| --- | --- | --- |
| [`v2`](uid/v2/Pieza.java) | mismo UID (`1L`), campo `precio` agregado | **lee OK** |
| [`v3`](uid/v3/Pieza.java) | UID cambiado a `2L`, misma estructura | `InvalidClassException` |
| [`v4`](uid/v4/Pieza.java) | **sin** UID declarado, campo `precio` agregado | `InvalidClassException` |

```
==============================================================
PASO 1 - Serializar con v1 (UID = 1L)
==============================================================
Escrito con v1: Pieza[codigo=ABC-123, cantidad=7]

==============================================================
PASO 2 - Leer con v2 : MISMO UID (1L), campo 'precio' agregado
==============================================================
LEIDO OK: Pieza[codigo=ABC-123, cantidad=7, precio=0.0]

==============================================================
PASO 2 - Leer con v3 : UID CAMBIADO a 2L, misma estructura
==============================================================
FALLO: InvalidClassException
  Pieza; local class incompatible: stream classdesc serialVersionUID = 1, local class serialVersionUID = 2

==============================================================
PASO 2 - Leer con v4 : SIN UID declarado, campo 'precio' agregado
==============================================================
FALLO: InvalidClassException
  Pieza; local class incompatible: stream classdesc serialVersionUID = 1, local class serialVersionUID = 5879301603476632054
```

Las tres filas dicen todo lo que hay que entender:

- **v2** — el UID es una **declaración del programador**: "esta versión es
  compatible con la anterior". La JVM la acepta y rellena el campo nuevo con su
  **valor por defecto** (`precio=0.0`). Los datos viejos se siguen leyendo.
- **v3** — cambiar el UID a mano es la forma de declarar una ruptura
  **deliberada**: los archivos viejos quedan explícitamente inservibles, con un
  error claro en vez de datos mal interpretados.
- **v4** — sin UID declarado, la ruptura es **accidental**. Nadie decidió romper
  nada: solo se agregó un campo. El UID calculado pasó de `1` a
  `5879301603476632054` y los datos existentes se volvieron ilegibles.

### Qué cambios son compatibles

Manteniendo el mismo UID, la especificación de serialización de Java considera:

| Cambio | ¿Compatible? |
| --- | --- |
| Agregar un campo | **sí** — al leer datos viejos queda en su valor por defecto |
| Eliminar un campo | **sí** — el dato viejo se ignora |
| Agregar o quitar métodos | **sí** — no forman parte del estado |
| Cambiar un campo a `transient` | sí, con pérdida del dato |
| **Cambiar el tipo** de un campo | **no** |
| **Renombrar** un campo | no — equivale a eliminar uno y agregar otro |
| Cambiar la jerarquía de herencia | no |
| Cambiar un campo de instancia a `static` | no — equivale a eliminarlo |

Los `static` no se serializan nunca: pertenecen a la clase, no al objeto. Es
también el motivo por el que `serialVersionUID` puede ser `static` sin
serializarse a sí mismo.

### La regla práctica

**Declarar siempre `serialVersionUID` en toda clase `Serializable`**, con un
valor arbitrario (`1L` sirve), y **cambiarlo solo cuando se quiera romper la
compatibilidad a propósito**.

El valor concreto es irrelevante; lo único que importa es que sea **estable**
mientras los cambios sean compatibles.

### El costo oculto de `Serializable`

Vale cerrar con la contra, que es la misma discusión del
[ejercicio 3](../ejercicio%203/3.md) sobre la herencia. Implementar
`Serializable` parece gratis —una interface sin métodos— pero:

- **Congela la representación interna** como parte de la API pública. Los campos
  privados pasan a ser un formato que otros ya guardaron en disco, y renombrar
  uno rompe la compatibilidad.
- **Esquiva los constructores**, y con ellos las validaciones e invariantes.
- **Es un riesgo de seguridad** al deserializar datos no confiables.

Por eso hoy, para intercambiar datos, se prefiere un formato explícito —JSON,
Protocol Buffers— donde la representación se declara aparte y no queda atada a
los campos de la clase. La serialización nativa sigue siendo útil para
persistencia local y de vida corta, que es el caso de este ejercicio.
