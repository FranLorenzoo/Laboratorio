# Ejercicio 4 · Clase `Logger` con patrón Singleton

## ¿Qué es el patrón Singleton?

Un **patrón de diseño** es una solución conocida y reutilizable para un problema
que aparece una y otra vez al programar. El *Singleton* (del inglés
*"single"*, único) resuelve este problema:

> Necesito que de una clase exista **una sola instancia** en toda la aplicación,
> y que cualquier parte del programa pueda llegar a ella.

Casos típicos: el registro de eventos (*logger*), la conexión a la base de
datos, la configuración de la aplicación, un caché. En todos ellos tener dos
objetos distintos sería un problema — dos loggers pisándose el archivo, dos
configuraciones que no coinciden, dos pools de conexiones duplicando recursos.

### Las tres piezas

| Pieza | Para qué |
| --- | --- |
| `private static Logger instancia;` | guarda la única instancia; es `static` porque pertenece a la **clase**, no a los objetos |
| `private Logger() { ... }` | **constructor privado**: impide que otras clases hagan `new Logger()` |
| `public static Logger getInstance()` | único punto de acceso; crea la instancia la primera vez y después devuelve siempre la misma; es `static` porque hay que poder llamarlo **sin tener todavía un objeto** |

El eje del patrón es el **constructor privado**, que es justamente lo que en el
[ejercicio 3.3](../ejercicio%203/3.3.md) aparecía como un error. La diferencia
es la intención: allá se quería heredar de la clase y el `private` lo impedía;
acá se busca deliberadamente que nadie más pueda instanciarla.

## Implementación

Archivos: [`Logger.java`](Logger.java) y [`TestLogger.java`](TestLogger.java).

```java
public class Logger {

    private static Logger instancia;          // 1. la única instancia

    private Logger() {                        // 2. constructor privado
        this.cantidadMensajes = 0;
    }

    public static Logger getInstance() {      // 3. punto de acceso
        if (instancia == null) {              // solo la primera vez
            instancia = new Logger();         // legal: estamos dentro de Logger
        }
        return instancia;
    }

    public void logInfo(String mensaje)    { registrar("INFO", mensaje); }
    public void logWarning(String mensaje) { registrar("WARNING", mensaje); }
    public void logError(String mensaje)   { registrar("ERROR", mensaje); }

    private void registrar(String nivel, String mensaje) { ... }
}
```

Los tres métodos públicos delegan en un método `private registrar(...)` que
concentra el formato del mensaje (hora + nivel + texto). Así, cambiar el formato
—o pasar a escribir en un archivo en vez de la consola— se hace en un solo
lugar.

## Sobre los modificadores de acceso

El enunciado pide pensarlos; este es el razonamiento:

- **Constructor `private`** — es la única forma de garantizar la unicidad. Si
  fuera `public`, cualquiera podría escribir `new Logger()` y tendríamos varias
  instancias, sin importar lo que haga `getInstance()`. En `TestLogger` está la
  línea comentada que lo demuestra:

  ```java
  // Logger log3 = new Logger();
  //   error: Logger() has private access in Logger
  ```

- **Atributo `instancia` `private static`** — `static` para que exista una sola
  copia asociada a la clase; `private` para que nadie la reemplace desde afuera
  con `Logger.instancia = otro;`.

- **`getInstance()` `public static`** — `public` porque es la puerta de entrada;
  `static` porque debe invocarse sobre la clase (`Logger.getInstance()`), no
  sobre un objeto que todavía no existe.

- **`registrar(...)` `private`** — detalle de implementación interno.

- **Efecto colateral:** como todos los constructores son privados, `Logger`
  tampoco puede ser **heredada** desde otra clase (ver ejercicio 3.3). En este
  caso es deseable: una subclase podría romper la garantía de instancia única.
  Si se quisiera hacerlo explícito, se declararía `public final class Logger`.

## Salida esperada

```
--- Primer acceso: se crea la instancia ---
>> Se creo la unica instancia de Logger <<

--- Los tres tipos de mensaje ---
[14:32:07] [INFO] Aplicacion iniciada correctamente
[14:32:07] [WARNING] La conexion tardo mas de lo esperado
[14:32:07] [ERROR] No se pudo abrir el archivo de configuracion

--- Segundo acceso: NO se crea otra instancia ---
log1 == log2 ?          true
log1.equals(log2) ?     true
hashCode de log1:       1329552164
hashCode de log2:       1329552164
...
```

Las pruebas que confirman el patrón:

1. El mensaje del constructor se imprime **una sola vez**, aunque
   `getInstance()` se llame varias veces.
2. `log1 == log2` da `true`: no son dos objetos iguales, son **el mismo objeto**
   (comparación de referencias, como se vio en el ejercicio 1.d).
3. Los `hashCode()` coinciden.
4. El contador de mensajes es compartido: los mensajes escritos "por `log2`"
   también los ve `log1`.

## Limitación: concurrencia

La versión implementada es la **inicialización perezosa** (*lazy*), que es la
que se pide habitualmente en el ejercicio, pero **no es segura con hilos**. Si
dos hilos ejecutan `getInstance()` a la vez, ambos pueden evaluar
`instancia == null` como verdadero antes de que ninguno haya asignado, y
crearse **dos** instancias.

Variantes que lo resuelven, de menor a mayor sofisticación:

**a) Método sincronizado** — simple, pero penaliza cada llamada:

```java
public static synchronized Logger getInstance() {
    if (instancia == null) {
        instancia = new Logger();
    }
    return instancia;
}
```

**b) Inicialización temprana (*eager*)** — la JVM garantiza que la inicialización
de los campos estáticos ocurre una sola vez:

```java
private static final Logger INSTANCIA = new Logger();

public static Logger getInstance() {
    return INSTANCIA;
}
```

Es segura y muy simple; la contra es que la instancia se crea aunque nunca se
use.

**c) *Holder* (inicialización bajo demanda)** — combina lo mejor de las dos:
segura, sin sincronización y perezosa, porque la clase interna no se carga hasta
la primera llamada a `getInstance()`:

```java
private static class Holder {
    private static final Logger INSTANCIA = new Logger();
}

public static Logger getInstance() {
    return Holder.INSTANCIA;
}
```

**d) `enum`** — la forma más robusta en Java: el propio lenguaje garantiza una
única instancia y además resiste la serialización y la reflexión:

```java
public enum Logger {
    INSTANCIA;

    public void logInfo(String mensaje) { ... }
}
// uso: Logger.INSTANCIA.logInfo("...");
```

## Críticas al patrón

Vale mencionarlas, porque el Singleton es de los patrones más discutidos:

- Introduce **estado global**, que dificulta razonar sobre el programa.
- Complica las **pruebas unitarias**: no se puede sustituir por un objeto falso
  con facilidad, y el estado persiste entre tests.
- Oculta las dependencias: una clase que usa `Logger.getInstance()` internamente
  no declara en ninguna parte que depende de un logger.

La alternativa moderna es la **inyección de dependencias**: crear una sola
instancia al arrancar la aplicación y pasarla por constructor a quien la
necesite. Se conserva la unicidad, sin el acoplamiento al acceso global.
