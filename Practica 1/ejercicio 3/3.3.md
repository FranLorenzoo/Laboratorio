# Ejercicio 3.3 · Constructores `private` y `protected` en la herencia

## Caso 1 — Constructores privados

```java
package laboratorio;

public class SuperClase {
    private SuperClase() {
    }
}
```

```java
package laboratorio;

public class SubClase extends SuperClase {
    public SubClase() {
    }
}
```

### ¿Es correcta la implementación?

**No.** `SubClase` no compila, aun estando en el **mismo paquete** que
`SuperClase`:

```
error: SuperClase() has private access in SuperClase
    public SubClase() {
                      ^
```

### Por qué

El constructor de `SubClase` genera una llamada implícita a `super()`, pero ese
constructor es `private`. Y `private` es el único modificador cuyo alcance **no
es el paquete sino la clase**: solo se puede usar dentro del cuerpo de
`SuperClase`. Que ambas clases compartan paquete es irrelevante.

Conviene separar dos cosas que suelen confundirse:

| Sentencia | ¿Compila? | Motivo |
| --- | :-: | --- |
| `public class SubClase extends SuperClase` | ✔ | `SuperClase` es `public` y no es `final`: heredar de ella es legal |
| el `super()` implícito del constructor | ✘ | el constructor es `private` |

Es decir: el error no está en el `extends`, sino en la imposibilidad de
**construir** la parte heredada del objeto. Y como todo constructor de subclase
está obligado a invocar a uno de la superclase, la clase queda inutilizable.

### La consecuencia importante

> Una clase cuyos constructores son **todos** `private` no puede ser
> heredada desde afuera de sí misma, ni instanciada con `new` desde otra clase.

Esto **no es siempre un error**: es una técnica de diseño deliberada. Se usa en:

- **Clases de utilidad** (`java.lang.Math`, `java.util.Arrays`): todo es
  `static`, no tiene sentido instanciarlas ni extenderlas.
- **Factory methods**: se oculta el constructor y se obliga a usar métodos
  estáticos de creación (`Integer.valueOf(...)`, `List.of(...)`).
- **El patrón Singleton**, que es justamente el [ejercicio 4](../ejercicio%204/4.md).

En este ejercicio, en cambio, es un error: se pretende heredar de una clase que
está diseñada para no ser heredada. Las dos intenciones son incompatibles.

### Soluciones

1. **Ampliar la visibilidad del constructor** — lo esperable acá:

   ```java
   protected SuperClase() { }   // o public
   ```

2. **Agregar otro constructor accesible**, dejando el privado para uso interno.

3. Si la restricción es intencional, **no heredar**: usar composición en lugar de
   herencia.

Un caso límite que sí funcionaría: si `SubClase` fuera una **clase anidada**
declarada dentro del cuerpo de `SuperClase`, el `private` sí sería accesible,
porque el alcance de `private` es toda la clase que la contiene.

## Caso 2 — Constructores protegidos

```java
package laboratorio;

public class SuperClase {
    protected SuperClase() {
    }
}
```

```java
package laboratorio1;

import laboratorio.SuperClase;   // ← falta en el enunciado

public class SubClase extends SuperClase {
    public SubClase() {          // ✔ VÁLIDA
    }
}
```

```java
package laboratorio1;

import laboratorio.SuperClase;   // ← falta en el enunciado

public class OtraClase {
    public OtraClase() {
    }

    public void getX() {
        new SuperClase();        // ✘ ERROR de compilación
    }
}
```

### ¿Es correcta la implementación?

**Parcialmente.** `SubClase` es válida; `OtraClase` no lo es.

Además, tal como está escrito el enunciado, **ninguna de las dos clases de
`laboratorio1` compilaría**, porque les falta el `import laboratorio.SuperClase;`
(o escribir el nombre completo `laboratorio.SuperClase`). Sin él, el error sería
previo: *"cannot find symbol: class SuperClase"*.

### `SubClase` — válida

El `super()` implícito invoca al constructor `protected` de una superclase de
**otro paquete**. Esto está expresamente permitido: el lenguaje autoriza el
acceso a un constructor protegido cuando se realiza mediante una **invocación de
constructor de superclase** (`super(...)`). Es el mecanismo que hace útil a
`protected` en los constructores: permite que la clase sea extendida desde
cualquier paquete, pero no instanciada libremente.

### `OtraClase` — inválida

```
error: SuperClase() has protected access in SuperClase
        new SuperClase();
        ^
```

`OtraClase` está en `laboratorio1` (otro paquete) y **no es subclase** de
`SuperClase`, así que no cumple ninguna de las dos condiciones que habilitan el
acceso `protected`.

### El detalle fino: con constructores la regla es más estricta

En el [ejercicio 2.e](../ejercicio%202/e.md) vimos que una subclase de otro
paquete puede acceder a un miembro `protected` siempre que el receptor sea de su
propio tipo. Con los **constructores** la restricción es todavía más dura:

| Forma de acceso desde otro paquete | ¿Permitida? |
| --- | :-: |
| `super(...)` dentro de una subclase | ✔ |
| `new SuperClase(){ }` (subclase anónima) | ✔ |
| `new SuperClase()` (creación simple) | ✘ |
| `SuperClase::new` (referencia a constructor) | ✘ |

Lo notable es que `new SuperClase()` está prohibido **incluso dentro de una
subclase**. Si `OtraClase` se declarara `extends SuperClase`, esa línea seguiría
sin compilar. La única forma de que una subclase de otro paquete ejecute ese
constructor es a través de `super()`, o sea construyendo un objeto **de su
propio tipo**, nunca un `SuperClase` "suelto".

La razón es la misma que en el ejercicio 2.e: `protected` habilita a las
subclases a construir *su propia* porción heredada, no a fabricar instancias
sueltas de la superclase en cualquier paquete.

### Soluciones para `OtraClase`

1. **Mover `OtraClase` al paquete `laboratorio`** → `new SuperClase()` pasa a ser
   válido por la regla del mismo paquete.
2. **Instanciar a través de la subclase**: `SuperClase obj = new SubClase();`
3. **Usar una subclase anónima**: `new SuperClase() { };` — legal, aunque
   conceptualmente es una forma de esquivar la restricción.
4. **Hacer `public` el constructor**, si la intención nunca fue restringir la
   creación.

## Resumen

| Situación | ¿Válido? | Motivo |
| --- | :-: | --- |
| Subclase de constructor `private`, mismo paquete | ✘ | `private` limita a la clase, no al paquete |
| Subclase de constructor `protected`, otro paquete | ✔ | `super()` está expresamente permitido |
| `new` de constructor `protected` desde otro paquete, sin herencia | ✘ | no cumple ninguna condición de `protected` |
| `new` de constructor `protected` desde otro paquete, siendo subclase | ✘ | solo `super()` o subclase anónima |
