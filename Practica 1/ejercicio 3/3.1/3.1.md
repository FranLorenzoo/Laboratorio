## a) y b) — Getters, setters y constructores

Cada subclase define **solo** sus variables propias (las cuatro de `Vacuna` se
heredan) con sus respectivos getters y setters, y un constructor que delega en
la superclase mediante `super(...)`:

```java
public VacunaGenetica(String marca, String pais_origen, String enfermedad_cura,
                      int cantidad_dosis, double temperaturaMinima, double temperaturaMaxima) {
    super(marca, pais_origen, enfermedad_cura, cantidad_dosis); // primero la parte heredada
    this.temperaturaMinima = temperaturaMinima;
    this.temperaturaMaxima = temperaturaMaxima;
}
```

Las tres redefinen además `toString()` reutilizando el de la superclase con
`super.toString()`, para no repetir el armado de los campos heredados.

## c) ¿Pudo compilar? ¿Qué problemas surgieron?

### El problema

Siguiendo el enunciado al pie de la letra —"todos ellos deben recibir los
parámetros necesarios para inicializar las variables de instancia **propias** de
la clase"— la primera versión del constructor fue:

```java
public VacunaGenetica(double temperaturaMinima, double temperaturaMaxima) {
    this.temperaturaMinima = temperaturaMinima;
    this.temperaturaMaxima = temperaturaMaxima;
}
```

**Esa versión no compila.** El error es:

```
error: constructor Vacuna in class Vacuna cannot be applied to given types;
    public VacunaGenetica(double temperaturaMinima, double temperaturaMaxima) {
           ^
  required: String,String,String,int
  found:    no arguments
  reason: actual and formal argument lists differ in length
```

### Por qué

Todo constructor de una subclase debe invocar, como **primera sentencia**, a un
constructor de su superclase. Si el programador no escribe ese llamado, el
compilador inserta automáticamente una llamada implícita a `super()`, es decir
**al constructor sin argumentos** de la superclase.

`Vacuna` declara un único constructor, el de cuatro parámetros. Y acá está la
regla clave: **el constructor por defecto solo se genera cuando la clase no
declara ningún constructor**. Como `Vacuna` declara uno, Java ya no agrega el
constructor vacío. Por lo tanto el `super()` implícito no encuentra a quién
llamar y la compilación falla.

Este es exactamente el mismo mecanismo que provoca el error del ejercicio
[3.2](3.2.md) con `java.io.File`.

### Cómo se solucionó

Se agregaron a cada constructor los parámetros de la superclase y se los delega
explícitamente con `super(...)` en la primera línea. Así, cada constructor sigue
inicializando sus variables propias, pero además garantiza que la parte heredada
del objeto quede correctamente construida.

### Alternativas evaluadas (y por qué se descartaron)

**Opción B — agregar un constructor sin argumentos a `Vacuna`:**

```java
public Vacuna() {
}
```

Compila, pero es peor: permitiría crear vacunas sin marca, sin país y con cero
dosis (`null`, `null`, `null`, `0`). Rompe la garantía de que todo objeto nace
en un estado válido, y traslada el problema a tiempo de ejecución en forma de
`NullPointerException`.

**Opción C — llamar a `super` con valores fijos:**

```java
public VacunaGenetica(double tMin, double tMax) {
    super("desconocida", "desconocido", "desconocida", 0);
    ...
}
```

Compila, pero inventa datos falsos y deja las variables heredadas inutilizables
desde afuera. También se descartó.

La **opción A** (propagar los parámetros al `super`) es la única que mantiene el
objeto consistente, y es la que se implementó.

## Salida esperada

```
--- toString() de cada subclase ---
VacunaPatogenoIntegro -> Vacuna [marca=Sinopharm, pais de origen=China, enfermedad que previene=COVID-19, cantidad de dosis=2] [virus patogeno=SARS-CoV-2 inactivado]
VacunaSubunidadAntigenica -> Vacuna [marca=Novavax, ...] [cantidad de antigenos=1, tipo de proceso=Proteina recombinante con adyuvante]
VacunaGenetica -> Vacuna [marca=Pfizer, ...] [temperatura minima=-80.0C, temperatura maxima=-60.0C]
```

En el bloque final, el arreglo está declarado como `Vacuna[]` pero cada elemento
imprime el `toString()` de su clase real: eso es **polimorfismo**, la decisión
de qué método ejecutar se toma en tiempo de ejecución según el objeto, no según
el tipo declarado de la referencia.
